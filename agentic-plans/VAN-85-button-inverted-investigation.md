# VAN-85 Button point 3: `inverted` on primary and shimmer (investigation)

**Ticket:** https://rankingcoach.atlassian.net/browse/VAN-85
**Ask:** `inverted` on `primary` and `shimmer`: a white fill, text in `--ado-face-start`, and on hover
`color-mix(in srgb, #fff 88%, var(--ado-face-start))`. It's for the "recommended card" in the webapp.

## 1. Is it breaking, and is it blocked on the theme?

**Not breaking. Not blocked.** It ships with fallbacks. The theme tokens are requested in
[VAN-85-button-inverted-theme-request.md](VAN-85-button-inverted-theme-request.md), but nothing waits on them.

### Tokens

| Name in the ask | In Vanguard / the generated theme? | Where it actually lives |
|---|---|---|
| `--ado-face-start` | **No** | Only in the design prototype `rc-webapp/tmp/ado hub/src/styles/tokens.css:78` (`#00495d`, derived from `--ado-base` with `oklch()`). |
| `--ado-text` | **No** | Same prototype, line 84 (`#006a85`). The ask doesn't need it. |
| `--ado-face-gradient-start` | **Yes**: `theming/direct-channel/direct-channel.min.css` and `.storybook/theming.css:82` | Generated by the webapp. It's `#00495d` (the same value as the prototype's `--ado-face-start`), and there's no dark-scheme override. The webapp already uses it (e.g. `AgentFace`, `MobileAppInviteConversationWidget`). |
| `--ado-base` | **Yes**: same files, `.storybook/theming.css:74` | Generated by the webapp: the brand's Ado colour (`#006a85`), the source the face colours are derived from. No dark-scheme override. |

So `--ado-face-start` in the ask is the prototype's name for the generated `--ado-face-gradient-start`. **Decision
(review): Vanguard uses `--ado-base` instead**, the brand's own Ado colour rather than the dark end of the face
gradient. It reads a bit lighter (`#006a85` vs `#00495d`) and still passes AA comfortably (see the table below).

### Decision: request tokens, implement against fallbacks

The muted button set the pattern: every colour reads a `--button-*` theme token, with the spec value as a fallback.
The same applies here:

```scss
--inverted-base: var(--ado-base, #006a85);
--inverted-fill: var(--button-primary-inverted-background-color, #fff);
--inverted-fill-hover: var(--button-primary-inverted-hover-background-color, color-mix(in srgb, #fff 88%, var(--inverted-base)));
--inverted-fg: var(--button-primary-inverted-text-color, var(--inverted-base));
--inverted-ring: var(--button-primary-inverted-focus-outline-color, #fff);
```

(and the same for `shimmer`, plus `--button-shimmer-inverted-sweep-color`).

Why tokens and not `--ado-*` used directly:

- White-label themes can restyle the button without editing Vanguard, as they do for every other button colour.
- The prototype already names them (`--button-primary-inverted-bg`, `-bg-hover`, `-fg`), so design and code line up.

The fallbacks are built on `--ado-base`, which already exists. Until the theme ships, the button looks
exactly as specified and follows each brand's Ado colour.

### Types

`inverted?: boolean` moves from muted-only to the shared non-muted props. It is documented as primary/shimmer only, and
Button ignores it on `default` and `secondary` (no class is added). I also tried a stricter split, with a separate
variant for primary/shimmer and `inverted?: never` on default/secondary. That **broke existing code**:
`HoverableCard.tsx:123` sets `type={ButtonTypes.default}` and then spreads `{...buttonProps}`, and the webapp has the
same pattern (`HoverableCard`, `PublishingBoardCTA`, `AIExtensionsTrigger`). So I kept the loose type. `blurred`,
`onDark`, `pressed` and `extraLarge` stay muted-only. `_ButtonInverted.spec.tsx` covers the types with
`@ts-expect-error`. Compared with the base branch, `tsc -p tsconfig.app.json` and `tsc -p tsconfig.spec.json` show
no new errors.

## 2. Design decisions

| Case | Behaviour |
|---|---|
| Rest | White fill, text and icon in `--ado-base`, border transparent (same box size as before) |
| Hover (`@media (hover: hover)`) | Fill `color-mix(in srgb, #fff 88%, var(--ado-base))` ≈ `#e0edf0`. No `brightness()` filter. |
| Shimmer sweep | **Kept**, as a faint band of the hover tint running over the white fill, with the same keyframes and 6s timing. On hover the two swap, so a white glint runs over the tinted fill. Reduced motion and `--ambient-play-state` work as before. The prototype simply drops the animation on white; keeping a faint sweep keeps shimmer distinguishable from inverted primary. |
| Focus | `:focus-visible` gets a 2px white outline with a 2px offset (the prototype's ring; the button sits on a dark surface). The regular primary focus look (hover fill and blue box-shadow) is reset. |
| Active / ripple | Ripple ink is the Ado base colour at 20%. |
| Disabled | Same colours, whole button at `opacity: 0.4` (it doesn't blend, so fading the button itself is safe), no sweep, `not-allowed` cursor. |
| Icon | Follows the text colour (`currentColor`) at rest, on hover and when disabled, as muted already does. |
| Dark mode | **Unchanged on purpose.** The button sits on its own dark/coloured surface, not on the page background, and `--ado-base` has no dark override. Contrast: `#006a85` on white ≈ 6.2:1, on the hover tint ≈ 5.2:1 (AA). |

## 4. What was done in Vanguard

- `Button.tsx`: `inverted` documented for primary/shimmer. The `.inverted` class is added only for muted, primary and
  shimmer. Inverted primary/shimmer icons follow `currentColor`, also when disabled.
- `_button-props.scss`: `filledInverted($name)` mixin, included from `Button.module.scss` on
  `.button-primary.inverted` and `.button-shimmer.inverted`.
- Stories: `Vanguard/Button › Button Type Inverted` and `… Inverted Dark Theme` (teal and dark surfaces: rest, icon,
  rounded, disabled; play tests check colours, sweep, disabled and the keyboard focus ring).
- Spec: `_ButtonInverted.spec.tsx` (runtime class and icon colour, and type-level checks).
